## Hazards
- lessons.md does not exist. Binding rules are auto-loop.md §9/§10 and CLAUDE.md.
- Migrations append-only (db.js:9-100; auto-loop §8 hotspot). Verified with node: `ALTER TABLE schedule ADD COLUMN cardio_id TEXT REFERENCES t(id) ON DELETE SET NULL` succeeds inside BEGIN..COMMIT with `foreign_keys=ON` and existing rows read back with `cardio_id: null`; adding it with a non-NULL DEFAULT fails ("Cannot add a REFERENCES column with non-NULL default value"). So the ALTER is viable only as nullable, no default.
- Existing schedule rows have `plan_id` nullable already (db.js:33, ON DELETE SET NULL). A cardio calendar entry would therefore be `plan_id NULL` + cardio ref, and existing code treats `planId` null as "(usunięty plan)" (app.js:98); `replaceAll` also nulls unknown planId (db.js:339). `getState` schedule SELECT lists columns explicitly (db.js:236) so the new column is invisible until added; `dayItems` must branch on it or cardio entries render as deleted plans.
- `workouts` table: `plan_name NOT NULL`, `plan_id` FK, all log rows come through `getLog()` (db.js:210-230) into `db.log`, which `viewJournal` renders assuming `exercises` (app.js:316) and `isDone`/`dayItems` match by `scheduleId`. Whether cardio workouts share `workouts` or get their own table is a design choice that changes every one of those consumers.
- `replaceAll` order (db.js:331): `DELETE FROM workouts; DELETE FROM schedule; DELETE FROM plans; DELETE FROM exercises;` in one `tx`. FKs are ON (db.js:129): workout_exercises/sets cascade from workouts; `workouts.schedule_id` is SET NULL. A new cardio_templates table referenced by `schedule` (SET NULL) / cardio workouts must be added to this DELETE list, and the delete order matters if any FK is RESTRICT/NO ACTION (default NO ACTION would make `DELETE FROM cardio_templates` fail while rows still reference it). Re-insert order: templates before schedule before workouts (as plans -> schedule -> log at db.js:337-340). Missing delete = old cardio rows survive an import of an older backup (D9).
- Old backup without cardio keys must still pass the array check at db.js:327; do not add cardio arrays to that required check.
- `GET /api/export` is a full `getState()` dump (server.js:65), so any cardio field added to `getState` also grows `/api/state`, which the frontend holds whole (app.js:44, 67).
- Deleting a plan leaves done schedule entries (db.js:277-278, CLAUDE.md). Same rule needed for template delete (D7): test with a schedule row linked to a workout, else the "unfinished only" rule is untested (auto-loop §10).
- Runner key: changing shape of `trening.run.v1` loses the owner's strength workout (auto-loop §9, §8); renderRunner/tick/visibilitychange/click handler all assume `run` is a strength run (app.js:468-471, 495, 508-517, 748). A cardio run object in a separate variable/key must not make `tick()` or `renderRunner()` touch the strength run, and `startRun` confirm text (app.js:369) only checks `run`.
- Audio unlock: `unlockAudio()` runs only on a click when `run` is truthy (app.js:748); the cardio countdown/interval beeps will be silent unless cardio start also calls `unlockAudio()` inside the click.
- `esc()` on every interpolated name (template names, interval labels); test with `<`, `"`, `&` (auto-loop §10). UI text, errors, comments in Polish; API URLs relative (`api/cardio...`, no leading slash).
- server.js has no `module.exports`/`require.main` guard and calls `createRepo(DB_PATH)` and `app.listen` at import (server.js:13,82); HTTP 400 for D2 "API" tests means spawning `server.js` with `PORT=3999 DB_PATH=<scratch>` or testing the repo throwing `ValidationError` (mapped to 400 at server.js:76). Never :3000 or `./data/trening.db`. `node --test` with no match exits 0; there are currently no test files (`ls` shows none).
- Dockerfile:11 `COPY server.js db.js ./` - any new top-level server file must be added (e.g. a shared validation module); files under `public/` need nothing.
- Wake lock is only requested when `run && run.phase !== 'summary'` (app.js:512, 495); a separate cardio session must call `keepAwake` itself, and `renderRunner` (called from `render()`, app.js:124) will call `keepAwake(false)` when `run` is null, releasing a cardio wake lock.
- `#runner` overlay is shared (index.html:25) with `body.style.overflow` set by `renderRunner` (app.js:511); a cardio full-screen view reusing it must coordinate with that.
