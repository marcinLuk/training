## Hazards
- auto-loop §8 hotspots: `useWorkout.ts`, `engine.ts`, `workoutStore.ts`, `planStore.ts`, `storage.ts`, `src/pwa/**`, `tokens.css`, `DESIGN.md` (owner decides). §9: time from timestamps through `clock.ts`; time rules checked on tap AND by a timer; corrupt-copy step never dropped; keys `trening.plans.v1`/`trening.workout.v1`; update blocked while a workout runs; violet only for cardio; stop (do not guess) if DESIGN.md lacks a cardio UI need. §10: tests must move the clock without ticks; reload tests need a fresh mount at each state (mid-interval, paused); old-shape fixtures; pin constants with literals; double tap 150 ms apart on each one-tap screen; Polish-letter names; phone width with `getBoundingClientRect`; build fixtures with app functions.
- Plan type narrowing: `Plan` has one shape and `validatePlan` :74 assumes `exercises` (error on empty :81). A cardio plan through it fails ("Dodaj co najmniej jedno ćwiczenie."). `toPlan` :46 and `savePlan` :138 rebuild only id/name/exercises, so a new field is silently dropped on save and load. `clonePlan` :55 and `summarizePlan` :130 also read `exercises`. Old plans have no `type`: `toPlan` must default to strength, and validation of strength must stay as is. `PlanEditor.vue:22` uses `reactive<Plan>`.
- A plan whose validation fails is dropped from the list and sets `unreadable` -> backup copy on next write (`planStore.ts:80-81`). A cardio plan read by an unchanged `toPlan` would count as unreadable and be copied aside.
- Workout state: `WorkoutState.version: 1` literal (`engine.ts:45`), and `parseWorkoutState` :98 accepts only strength shape. A cardio state in the same key makes an older reader copy it to `.corrupt` (`workoutStore.ts:168`). Any new shape must keep old strength JSON parsing unchanged (no `kind` field = strength; tests must start from old-shape data, §10).
- `App.vue:70-81`: `view.mode` 'set'|'rest'|else = end screen. A cardio view with another `mode` would fall into `WorkoutEnd`. `workoutRunning` `App.vue:23` = `view.value !== null`, so the cardio session must produce a non-null state/view, or updates reload mid-session. `askEnd` :241 uses `state.mode`.
- `useWorkout.ts` strength coupling: `armExpiry` :115-124 and `expireIfIdle` :128 expire any non-finished state by `lastActivityAt` — a running cardio session must NOT expire (PRD OQ4); only paused time counts. `restoreWorkout` :44-52 expires by `lastActivityAt` and calls `resolveRest`. `commit` :91 `screenChanged` uses `cursor`/`mode`. Display timer :268 runs only in rest mode; cardio needs its own render timer (it only asks for render) plus a sound scheduler. `refresh` :147-161 sound rule is rest-only (`playRestEnd`). `visibleSince` :76 logic is the model for the visible/late (<= 2 s) check; the 3 s countdown beeps need the same check for each beep.
- Tick/Date.now reads: `useWorkout.ts:74,76,119,60,66` all use `now()` (good). Direct `Date.now()` only as defaults in `planStore.ts:132,161`. `setInterval(refresh, 250)` at :272 only triggers a render (`clockMs`). A cardio engine must not count ticks.
- `wakeLock.ts` is shared and global (`wanted` flag :10); `syncWakeLock` :79-82 must also hold for a running or paused cardio state.
- `src/pwa/updatePolicy.ts` takes booleans, so no change if App passes `true` for cardio; `useServiceWorkerUpdates.ts` unchanged.
- `tokens.css` has no cardio tokens or the three cardio sizes: adding them is allowed only as DESIGN.md values (:24-25, :234-236); no other new colors. Dark theme only.
- `sound.ts` has one function; the new sounds need `unlockAudio()` inside the Start tap (`useWorkout.start` :177 does this). The countdown beeps need distinct work-start vs rest-start sounds; keep `playRestEnd` and its tests unchanged (strength guardrail).
- Lock mode state: DESIGN.md :340 says reload removes the lock, so it must live in memory only, not in `trening.workout.v1`.
